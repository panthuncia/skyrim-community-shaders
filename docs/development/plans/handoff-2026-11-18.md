# Handoff, 2026-11-18

For a new session picking up the Community Shaders (CS) render-graph work. Read this first, then the documents it points to.

## 1. What this work is

CS renders Skyrim through OpenRenderGraph (ORG) on BasicRHI. One recipe of CS-owned stages draws the frame. The engine supplies
data only. There are three modes:

| Mode | How to select | Backend |
|---|---|---|
| Guest (default) | nothing | ORG shares DXVK's Vulkan device |
| Native | `CS_ORG_NATIVE=1` | BasicRHI on Vulkan or D3D12, no DXVK |
| Plain D3D11 | `CS_ORG=0` (cs-test config `d3d11`) | the engine's own D3D11 path |

`Native::GraphMode()` is true in guest and native. The Drawcall Limit Fix feature (DCLF) draws the scene in both.

The design rules the user has set, which every change must keep:

- Errors are fatal. No retries, fallbacks, timers or waits.
- The render thread never waits.
- New versions of anything publish only at frame boundaries.
- One code path for native and guest where possible.
- A graph is never rebuilt inline. Builds are asynchronous and are adopted at the next frame's Begin.

Main design document: `docs/development/org-native-frame-graph.md` (long, dated sections, newest at the end).
Others: `render-graph.md`, `dclf-architecture.md`, `dclf-validation.md`, `dclf-open-defects.md`, `testing.md`.

## 3. Rules for working here

- Never touch, commit or clean `extern/dxvk`.
- Game runs: background (`CS_TEST_BACKGROUND=1`) unless the user allows foreground, one launch per shell call, no clicks or
  synthetic input, never raise a timeout. A cold shader store is the usual reason for a slow run. Warm-up runs with a long
  timeout and `cs.hang_watchdog=0` are allowed.
- The test machine has an AMD RX 6600. Set `DXVK_DEBUG=hang` on every run. Never arm RGD crash capture around a run.
- The MO2 modlist must keep `+CS AB nfg`, `+Start On Save` and `*TerrainHelper.esp`. MO2 and Skyrim may be closed before a run
  without asking.
- Frame generation (DLSS-G) needs a foreground run. Ask first.
- Commits: conventional, title at most 50 characters, body wrapped at 72, no attribution lines, submodules first.
- No builds of old revisions. No verification builds whose outcome is already known.
- Comments: one line, two at most, plain language, the why and not the what. Longer only at the top of a file.
- Shaders: never write an early exit behind an `||` of equality tests (`AGENTS.md`, AMD RDNA2 miscompile).
- Editing a shader header under `Common/` invalidates about 1,700 Lighting variants. A cold compile takes about 90 seconds.
- Subagents: do not resume one that has been idle an hour or whose context is over half full. Start a new one with a summary.
  With two or more agents in one worktree, the coordinating session builds and commits.

## 5. What is left: the two plans

Neither is started. The user has answered the open questions for both. Do not start either without the user saying so.

### 5a. Frame revision (event-driven resources)

- **Plan:** `docs/development/plans/frame-revision-plan.md`. Background: `frame-revision-investigation.md` beside it.
- **Goal:** nothing checks "do we need to resize" during a frame. A change to a variable raises an event. Resources that depend
  on the variable are remade. Graphs that depend on those resources are rebuilt asynchronously. A frame adopts the latest
  prepared set at Begin, atomically. This is how DCLF already works, and DCLF joins the shared system last.
- **Shape:** ten steps. The system lives in ORGModuleServices with small ORG additions. Settings move to `Setting<T>`, with a
  list in the plan to work through. Intermediate scaffolding is allowed during the port and must be gone at the end.
- **Decisions recorded in the plan:** options 1c, 2c, 3a, 4a, 5a, 6a, 7a, 8a. A change that would recreate device-level objects
  stays fatal until one is actually met. The VRAM cost of holding two sets during a switch is accepted for now.
- **Section 11** holds later findings that the plan must cover: the swap chain colour space must switch in the same adoption as
  the HDR content (today it switches up to 10 frames apart, which shows as wrong colours on an HDR toggle), a per-frame HDR
  switch test, and a rule for SDK contexts with frames in flight. Finding notes: `xess-tdr-hdr-colours.md`.
- **What it retires:** the tactical fixes in item 3 above, including `RegisterAtBoundary`, `g_registrationRatios`,
  `Driver::AtNextBegin` size requests, `HDRDisplay::PostChainTarget` and the consecutive-registration warning.

### 5b. Native frame generation

- **Plan:** `docs/development/plans/native-frame-generation-plan.md`. The decisions table is in its section 6. All seven
  questions were answered (a).
- **Goal:** frame generation in the native modes. Today it works only in guest.
- **Shape:** a `FrameGen::Presenter` interface with a DXVK backend and a native backend. Streamline stays the runtime.
  `sl.fsr_g` gets a D3D12 backend. Native Vulkan comes first.
- **Step 1 is piece A7:** the hudless copy and the HDR output become steps of the UI stage. That also removes the last own-epoch
  machinery that C3 had to leave in place.
- Note: FSR frame generation is CS's own `sl.fsr_g` Streamline plugin. It is not in DXVK's presenter.
