# P4.5: engine buffers on ORG

Reverse engineering and design for plan task P4.5 ([org-full-port.md](../org-full-port.md), Phase 4): the engine's
vertex and index buffers, `BSGraphics::TriShape` ownership, and the dynamic ring. Found with Ghidra (GhidraMCP) and the
Address Library on 2026-11-10, SE 1.5.97 and AE 1.6.1170. It extends R6.4 and R6.5 of
[engine-d3d11-surface.md](../engine-d3d11-surface.md), and corrects one point of the plan row (below).

## What changes the plan row

- **75592 is not a vertex or index buffer function.** It creates the constant buffer pools (R3). Static geometry buffers
  are created by three functions behind the geometry facade (below), and 75593 creates the dynamic ring. Constant
  buffers do not share either path: they are DYNAMIC buffers mapped with WRITE_DISCARD by the shaders' Setup functions,
  and they belong to P2.6/P5.7. P4.5 leaves them alone.
- **A tripwire handle cannot sit in a TriShape while DXVK's context is the engine's.** DXVK's `IASetVertexBuffers` and
  `IASetIndexBuffer` cast the pointer to `D3D11Buffer` (`d3d11_context.cpp`), so a handle crashes there. Handles go in
  only when P4.1's wrapping context is the engine's (`Tripwire::GuestContextInstalled()`, `CS_ORG_TRIPWIRE_GUEST=1`).
  Otherwise the field keeps the guest DXVK buffer made from the ORG buffer, and `Tripwire::AttachGraphResource` ties the
  ORG buffer to it.
- **The guest wrapper has no CPU access.** `dxvkCreateBufferFromVkBuffer` accepts only DEFAULT usage. So the ring cannot
  stay a DYNAMIC D3D11 buffer the engine maps: CS replaces the map function, and the engine never calls `Map` on it.

## Static geometry: the creation functions

Every engine call goes through the geometry facade, `BSShaderResourceManager` (vtable SE 305902 `0x14186bf80`, AE
255472 `0x141ac5610`; CommonLib `RE::VTABLE_BSShaderResourceManager`). Each slot is a thunk `lea rcx,[Renderer]; jmp fn`
(Renderer SE `0x143028490`, AE `0x1432887c0`). Same slot layout in SE and AE:

| Slot | SE ID / addr         | AE ID / addr          | What it does                                                                                                                            |
| ---- | -------------------- | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 0x10 | 75473 / 0x140d6b8d0  | 77259 / 0x140e45d30   | `CreateTriShape(Renderer*, NiStream*, VertexDesc, uint vertexCount, uint indexCount)`: VB and IB                                        |
| 0x18 | 75476 / 0x140d6be60  | 77262 / 0x140e462c0   | `CreateTriShapeSharedVertices(Renderer*, TriShape* source, VertexDesc, const uint16* indices, uint indexCount)`: shares the VB, new IB |
| 0x20 | 530710 / 0x140d6c310 | 77266 / 0x140e46800   | TriShape IncRef: `lock inc [rdx+0x18]`                                                                                                  |
| 0x28 | 75480 / 0x140d6c320  | 77267 / 0x140e46810   | `ReleaseTriShape`                                                                                                                       |
| 0x48 | 75481 / 0x140d6c3a0  | 77268 / 0x140e46890   | `CreateDynamicTriShapeData(Renderer*, NiStream*, VertexDesc, uint vertexCount, uint indexCount)`: static VB stream and IB             |
| 0x50 | 530711 / 0x140d6d130 | 77279 / 0x140e47710   | dynamic data IncRef: `lock inc [rdx+0x20]`                                                                                              |
| 0x58 | 75492 / 0x140d6d140  | 77280 / 0x140e47720   | `ReleaseDynamicTriShapeData`                                                                                                            |

The draw slots (0x30, 0x38) are R1's.

Each creator calls `(*(Renderer+0x48))->CreateBuffer` (vtable +0x18), which is RendererData's device (RendererData starts at
Renderer+0x10, device at +0x38). The descriptions, from the decompiles:

| Buffer                                    | ByteWidth                               | Usage   | Bind       | CPU access | Initial data                                     |
| ----------------------------------------- | --------------------------------------- | ------- | ---------- | ---------- | ------------------------------------------------ |
| 75473 / 75481 VB                          | `((desc & 0xF) * 4) * vertexCount`      | DEFAULT | VERTEX (1) | 0          | the raw vertex copy, read from the stream first  |
| 75473 / 75476 / 75481 IB                  | `indexCount * 2`                        | DEFAULT | INDEX (2)  | 0          | the raw index copy                               |

The structs:

- `TriShape` (0x30, 75473/75476): VB +0x00, IB +0x08, VertexDesc +0x10, refcount +0x18 (starts at 1), raw vertices
  +0x20, raw indices +0x28. 75476 takes the VB from the source shape through 74735 (`0x140d4e060`), which AddRefs it and
  copies the raw vertex block.
- Dynamic data (0x38, 75481): VB +0x00 (stream 0, static), IB +0x08, VertexDesc +0x10, ring offset +0x18 (starts at -1),
  dynamic stride x count +0x1c (`((desc >> 2) & 0x3c) * vertexCount`, stream 1), refcount +0x20, raw vertices +0x28, raw
  indices +0x30. The per-frame stream 1 goes through the ring.

Direct callers besides the facade: 75681 (`0x140d7a180`, reached from 75682's 0x140d7a6d0) calls 75476 and 75480. It
rebuilds a skin partition from legacy per-partition data **(inferred from the decompile: bone weights and indices are
repacked)**. Nothing else calls the three creators directly (xrefs: the facade thunks and the Address Library table).

Threads: the creators run wherever a NIF loads (`NiStream`): BSResource's loader threads for queued loads, the
requesting thread for blocking ones **(inferred, as in R6.5; a thread-ID log on 75473 would settle it)**. None of them
takes `Renderer::Lock`. Releases (75480, 75492) run on whichever thread drops the last reference: atomic decrement, then
`Release` on the IB, then the VB, then the raw copies are freed. Nothing orders a release against the GPU: D3D11's
deferred destruction covers it today.

Not covered by these functions, and kept on D3D11 by P4.5:

- 75593's quad index buffer (`0x143025f38`, 524734) and particle corner VB (`0x143025f40`, 524735). They are created in
  `InitD3D`, before the render graph exists.
- Any buffer a mod creates and stores in a TriShape itself (RaceMenu-style body morphs copy a partition with new buffers,
  [dclf-architecture.md](../dclf-architecture.md) "Body morphs").

Ghidra renames (both databases where the function exists there): `CreateTriShapeSharedVertices`,
`CreateDynamicTriShapeData`, `ReleaseDynamicTriShapeData`, `UnmapDynamicBuffer`, `UnmapDynamicTriShapeDynamicData`,
`UnmapDynamicLineShapeDynamicData`. The AE database has no function boundary at 77259 and 77267 (they sit inside
`FUN_140e45ba0` and `FUN_140e467d0`); their first 24 bytes match SE's, and the facade thunks jump to them.

## The dynamic ring

R1 has the algorithm. The globals, with their Address Library IDs:

| What                    | SE ID / addr         | AE ID / addr         |
| ----------------------- | -------------------- | -------------------- |
| `ID3D11Buffer* ring[3]` | 524731 / 0x143025f18 | 411350 / 0x143286a20 |
| `uint cur`              | 524732 / 0x143025f30 | 411351 / 0x143286a38 |
| `uint offset`           | 524733 / 0x143025f34 | 411352 / 0x143286a3c |
| `bool safe[3]`          | 524742 / 0x143026164 | 411358 / 0x143286a78 |
| `ID3D11Query* fence[3]` | 524743 / 0x143026168 | 411357 / 0x143286a60 |
| immediate context       | 524771 / 0x143027ea0 | 411391 / 0x1432887b0 |

Functions:

| Function                                    | SE ID / addr        | AE ID / addr        | Callers                                                                                         |
| ------------------------------------------- | ------------------- | ------------------- | ----------------------------------------------------------------------------------------------- |
| `MapDynamicBuffer(Renderer*, size, &off)`   | 75484 / 0x140d6c8a0 | 77271 / 0x140e46d60 | 75486, 75490, 75491 (x2), 75497, `RenderPassImmediately_Standard`                                |
| `UnmapDynamicBuffer(Renderer*)`             | 75485 / 0x140d6c9e0 | 77272 / 0x140e46ea0 | `RenderPassImmediately_Standard`                                                                 |
| `UnmapDynamicTriShapeDynamicData(...)`      | 75487 / 0x140d6ca30 | 77274 / 0x140e46ef0 | the geometry dispatcher, types 1 (particles) and 4 (dynamic TriShape)                            |
| `MapDynamicLineShapeDynamicData(...)`       | 75497 / 0x140d6d5d0 | 77287 / 0x140e47ba0 | the dispatcher, type 13 (calls 75484)                                                            |
| `UnmapDynamicLineShapeDynamicData(...)`     | 75498 / 0x140d6d5f0 | 77288 / 0x140e47bc0 | the dispatcher, type 13                                                                          |

The three unmap functions are byte-identical: `ctx->Unmap(ring[cur], 0)`. 75490 and 75491 unmap inline. The users read
`ring[cur]` when they bind it (75489, 75490, 75491, 75499, 75500), so the pointer in `ring[cur]` only has to be right
between a map and the draw that follows it. Nothing outside these functions reads the ring globals (no CS code does).

The map runs on whichever thread drives the immediate context under `Renderer::Lock`: the render thread, or the loading
screen's ServingThread (R6.2).

DXVK's `Unmap` of a buffer does nothing (`D3D11ImmediateContext::Unmap` only unmaps images), so the engine's unmaps would
be harmless on a guest buffer. CS skips them anyway while the ORG ring is active, so the contract does not depend on that.

## What CS does with `CS_ORG_ENGINE_BUFFERS=1`

Code: `src/RenderGraph/Engine/Buffers/`. Hook registrations only in `Hooks.cpp`.

### Static VB/IB

- 75473, 75476 and 75481 are detoured. Each marks its thread as creating engine geometry and calls the original.
- The device's `CreateBuffer` (vtable slot 3, detoured on DXVK's device at `InitD3D`) serves, on such a thread, a request
  for a DEFAULT VERTEX or INDEX buffer with initial data: it makes an ORG buffer in `HeapType::GPUUpload` memory
  (device-local and host-visible when the GPU has resizable BAR, host memory otherwise), copies the initial data through
  its persistent mapping, and wraps it as a guest DXVK buffer (`RenderGraphRuntime::WrapBuffer`). No GPU copy is needed:
  the CPU writes finish before the engine can see the buffer, and every later queue submission makes host writes visible.
- The engine gets a tripwire handle wrapping the guest buffer when P4.1's guest context is installed, else the guest
  buffer itself with the ORG buffer attached (`Tripwire::AttachGraphResource`).
- Releases need nothing new: the TriShape's `Release` reaches the handle or the guest buffer from any thread, and the ORG
  buffer goes through `Tripwire::ServiceRetired` to `ReleaseAfterD3D11`, after DXVK has dropped its own bindings.
- Any failure (the render graph not active yet, an allocation failure, DXVK refusing the wrap) falls back to D3D11 for
  that buffer. Buffers made before the render graph starts stay D3D11 for their life.

### The dynamic ring

- 75484 is detoured. The first map after the render graph is active switches the engine to an ORG ring: chunks of 4 MiB
  in `GPUUpload` memory, persistently mapped, each wrapped as a guest buffer (or a handle wrapping one).
- A map bumps an offset in the current chunk, as the engine does (no alignment). When the chunk is full it is retired
  through `RenderGraphRuntime::ReleaseAfterD3D11`: it comes back to the free list once the GPU is past every D3D11 command
  issued so far, which `SignalFramePace` checks each frame. That replaces the engine's event query and its spin: the next
  chunk is a free one, or a new one. Frames never wait.
- On each chunk change CS writes the chunk's buffer into `ring[cur]` (cur advancing mod 3, as before), keeping one
  reference per slot, so whatever the engine does with the slots at shutdown stays balanced.
- 75485, 75487 and 75498 return at once while the ring is active.
- If a chunk cannot be made after the switch, the engine's own three buffers go back into `ring[]` and the original map
  runs from then on.

### DCLF

`GpuResources::Acquire` asks `Buffers::Resolve` first. A buffer the ORG owns (a handle or a guest buffer with an attached
ORG buffer) is read directly: its VkBuffer, size and device address come from the ORG buffer, with no DXVK description,
no pinning and no relocation. The lease still holds a reference on the engine's object, so the ORG buffer outlives the
lease as it did the DXVK buffer. `Prefetch` skips those buffers. GrassOptimizations unwraps engine buffers before it binds
them to DXVK's context.

## Risks

- **Without resizable BAR** `GPUUpload` falls back to host memory: vertex fetch then crosses PCIe. All loaded geometry
  is a few hundred MB, so this is a real cost there. A staged copy into device-local memory through the copy queue would
  remove it, but needs an ordering point before the guest's first draw of the buffer.
- **Third-party plugins** that read `TriShape::vertexBuffer` and pass it to DXVK themselves crash once handles are in the
  fields (`CS_ORG_TRIPWIRE_GUEST=1`). Without that switch they get a DXVK buffer, as before.
- The thread inference for the creators: if a creator runs on a thread that already holds an ORG lock the render thread
  waits on, the ORG allocation could deadlock. Nothing seen suggests this; the buffers are made with ECS registration
  suppressed, as DCLF's pooled backings are off the render thread.
