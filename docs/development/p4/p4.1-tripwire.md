# P4.1 Tripwire handles: engine side

The RE behind the tripwire handles ([org-full-port.md](../org-full-port.md) P4.1) and the API the other P4 lanes use. The
handles themselves are described in [render-graph.md](../render-graph.md) ("Tripwire handles"). Found with Ghidra and
the Address Library on 2026-11-10, SE 1.5.97 and AE 1.6.1170. AE 1.7.104 is not checked.

## Which interfaces the engine asks for

Every IID constant in the executable was searched for (its 16 bytes in `.rdata`), and then every reference to it. The engine
calls `QueryInterface` (or `GetBuffer` with an IID) in only these places, the same on SE and AE:

| IID                   | SE caller (ID / address)                                                  | AE caller (ID / address)                                                    | On what                                                        |
| --------------------- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `ID3D11Texture2D`     | `CreateSwapChainViews` 75590 / 0x140d71d3b                                 | 77397 / 0x140e4cc6b                                                         | swap chain `GetBuffer(0)`                                      |
| `ID3D11Texture2D`     | `SaveRenderTargetToFile` 75522 / 0x140d6e7ac                               | 0x140e48efc                                                                 | swap chain `GetBuffer`, for kFRAMEBUFFER only                  |
| `ID3D11Texture1D/2D/3D` | texture save helper 75819 / 0x140d87b20                                  | 77641 / 0x140e64660                                                         | the render target's texture (see below)                        |
| `IDXGIDevice`, `IDXGIAdapter`, `IDXGIFactory` | `Renderer::CreateSwapChain` 75457 / 0x140d69eca          | 0x140e44394                                                                 | the device, then its adapter and factory                       |
| `IDXGIDevice1`        | `InitD3D` 75595 / 0x140d7288f                                              | 77403 / 0x140e4d66f, and `Renderer::Init` 0x140e426cd                        | the device (`SetMaximumFrameLatency(2)`)                       |
| `IDXGIFactory`, `ID3D11InfoQueue` | `CreateDeviceAndSwapChain` 75589                               | 77396                                                                       | before any handle exists                                       |
| `ID3D11Debug`         | `Renderer::Shutdown` 0x140d694dc                                           | 0x140e432dc                                                                 | the device, at exit                                            |

Nothing in the engine asks a texture or view for `IDXGIResource`, `IDXGISurface`, `ID3D11Resource` or `ID3D11View`, and
nothing asks for `ID3D11Device1+` or `ID3D11DeviceContext1+`. A handle's chain (`IUnknown`, `ID3D11DeviceChild`,
`ID3D11Resource`/`ID3D11View`, its own interface) therefore covers every engine query on resources and views. On the
device, the IDXGI queries are expected: a guest device forwards them (one logged line per site), and the native build
(P6.1) has to answer `IDXGIDevice1` with something whose `SetMaximumFrameLatency` succeeds.

**The texture save helper (75819 / 77641)**, reached from `SaveRenderTargetToFile` (75522) through 75598 and from 75526
(R11), shows how the engine probes: `GetType` (vtable +0x38), then `QueryInterface` for the one texture interface that
matches, `GetDesc` (+0x50), `device->CreateTexture*` for a staging copy, then `context->CopyResource(staging, texture)`
(+0x178) and `Map`. So:

- A texture handle must answer `GetType` and `GetDesc` itself. It does in both modes.
- A query for another D3D11 object interface (`ID3D11Texture3D` on a 2D texture) is refused quietly, with no tripwire
  line, because the real object refuses it too.
- `CopyResource` gets the handle as an argument, so it works only through the guest context, which unwraps it.

**`GetResource` and `GetDevice`.** A view made with its resource answers `GetResource` with that resource (a handle when
the lane passed one). `GetDevice` on a resource or view is a tripwire in native mode and forwarded in guest mode. No
engine caller was found that needs it: the engine always uses the device global or `RendererData +0x38`. A paired guest
context answers `GetDevice` with the guest device, and the guest device answers `GetImmediateContext` with the guest
context.

## The guest device and context

The engine's device and context pointers (all written once by device creation, SE 75589 / AE 77396):

| Pointer                  | SE                            | AE                            | Readers                                                              |
| ------------------------ | ----------------------------- | ----------------------------- | -------------------------------------------------------------------- |
| Device global            | 524729 / 0x143025f08          | 411348 / 0x143286a10          | 32 functions (R11), CS `ShaderCompiler.cpp`                          |
| Immediate-context global | 524771 / 0x143027ea0          | 411391 / 0x1432887b0          | 110 functions (R1: the Renderer block, Setup*, ImageSpace)           |
| `RendererData +0x38`     | `Renderer +0x48` (`forwarder`) | the same through `GetRuntimeData()` | state-object creation (R2), `CreateTriShape` (R6.5), Scaleform   |
| `RendererData +0x40`     | `Renderer +0x50` (`context`)  | the same                      | Scaleform, CS `globals::ReInit`                                      |

Scaleform reads `+0x48/+0x50` through `GetScaleformRendererParameters` (75576 / 77378) once, in its renderer setup
(80603 / 0x140edb730, which calls the HAL's vfunc +0x1a8 with them). That runs in `BSScaleformManager`'s constructor
(0x140ece0d0), which the main init (0x1405ae010) calls **after** `Renderer::Init` (75445). The install in the InitD3D hook
therefore reaches Scaleform too.

`InstallGuestDevice` runs in CS's existing `BSGraphics_Renderer_Init_InitD3D` thunk (SE 75595+0x50, AE 77226+0x2BC), right
after the original. It checks that the globals and `RendererData` hold the same objects, makes a device handle and a
context handle that wrap them, pairs them, and writes the handles into all four pointers. `globals::ReInit` unwraps them,
so `globals::d3d::device`/`context` stay DXVK's own objects. That matters because:

- CS's D3D11 hooks are `detour_vfunc` on DXVK's vtables. A guest handle forwards through those vtables, so the hooks
  still see every engine call, with handle arguments already unwrapped.
- DXVK's private exports cast their arguments to DXVK's classes.
- CS's own calls skip the forwarding.

What the engine's later init does through the guest device (75592 and 75593 create their buffers, the `IDXGIDevice1`
query) returns DXVK's own objects, which are not handles.

**References.** The engine holds one reference to the device and one to the context. After the install, the engine's
pointers hold the handles with one reference each, and a second reference on each is never dropped. DXVK's objects keep
the engine's original reference and the handle's own. An engine `Release` at shutdown therefore frees nothing still in
use, and DXVK's device outlives the handles. It leaks only at process exit.

**Threads.** The install runs on the main thread during `Renderer::Init`, before the loading-screen thread or loader
threads use D3D11 (R6.1). The handles forward from any thread. The loading-screen loop (38085), loader threads and Bink all
reach DXVK through them.

## Release and the GPU free

R6 says resources are created and released without `Renderer::Lock`, on loader threads (TriShape 75480 / 77267, textures
75527 / 77322).

- **A handle's last Release** (any thread) releases the wrapped DXVK object at once and queues the ORG resource and the
  owner on a mutex-guarded list. The render thread drains the list at the frame pace point (`ServiceRetired`) into
  `RenderGraphRuntime::ReleaseAfterD3D11`. That issues an event query and drops them once the GPU has passed every D3D11
  command issued until then.
- **The wrapped DXVK object can outlive the handle**: DXVK's context keeps a reference while the object is bound, and a
  forwarded getter hands it out. In guest mode the handle therefore tags the wrapped object
  (`SetPrivateDataInterface` with a CS GUID) with its own references to the ORG resource and owner. DXVK destroys the
  object only after its last binding is gone, possibly on its CS thread. Then the tag goes through the same queue. The
  memory is freed after the later of the two.
- **Lanes that keep plain DXVK objects** in engine fields (no handle, the default while the guest switch is off) tag them
  with `AttachGraphResource` at creation and get the same lifetime and lookup.
- The queue is never destroyed, so a tag that dies during static destruction still has somewhere to go.

## Caller attribution

`DescribeCaller` names a game address as `SkyrimSE.exe+0xd6a8f2 (ID 75467+0x82)`. The ID is the nearest Address Library
entry at or before the offset, within 0x4000 bytes (`REL::Offset2ID`, built once). Any other module is shown as
`Module.dll+0x1234`. A module other than CS also gets "(another plugin calls D3D11: see org-extension-api-notes.md)".

`IsHandle` now first checks that the object's vtable lies in CS's own image (`SizeOfImage` from its PE header). That makes
the check on every argument of every forwarded engine call a single range compare for DXVK's objects.

## The API for P4.2-P4.7

All in `src/RenderGraph/Engine/Tripwire/Tripwire.h` unless noted. The earlier API is unchanged; everything below is
additive.

| Call                                                                    | Use                                                                                                                                      |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `Create<Type>(desc, Options{ name, graph, owner, watch }, wrap)`         | A handle per type: textures 1D/2D/3D, buffer, the four views, VS/PS/CS, input layout, the four states, query, context, device, swap chain. `wrap` is the DXVK object made from the ORG resource (guest), or null (native). |
| `GuestContextInstalled()` (`GuestDevice.h`)                             | Whether the engine's device and context are guest handles (`CS_ORG_TRIPWIRE_GUEST=1`). Install handles in engine fields only when true. |
| `GraphResourceOf(pointer)`                                              | The ORG resource behind any engine field value: a handle, a tagged DXVK object, or a guest handle's wrapped object. Null otherwise.        |
| `AttachGraphResource(object, graph, owner)`                             | Tags a plain DXVK object: lookup plus a deferred free when DXVK destroys it.                                                              |
| `Unwrap(pointer)`                                                       | What to hand `globals::d3d::context`/`device` or a DXVK export. A non-handle comes back as is.                                            |
| `Describe`, `IsHandle`, `ShaderBytecode`, `InputElements`               | As before.                                                                                                                               |
| `PairDeviceAndContext(device, context)`                                 | Pairs a device handle and a context handle (the guest install uses it; P6.1 will too).                                                   |
| `ServiceRetired`, `TakeRetired`                                         | As before (called from the frame pace point).                                                                                            |

## Open questions

1. `IDXGIDevice1::SetMaximumFrameLatency` in native mode (P6.1). The guest device forwards it.
2. Engine code that compares pointers it gets back from a forwarded getter (`OMGetRenderTargets`, `GetResource` on a
   DXVK view) with handle fields. None was found in the IID survey; the guest log's `passed on` lines show where engine
   code still feeds handles to D3D11, not where it compares them.
3. CS hooks on DXVK's context vtable that compare their arguments with engine fields see unwrapped objects once a lane
   puts handles in those fields. Each lane checks the hooks that read its fields (`Hooks.cpp`, `State.cpp`, DCLF's
   `PassCapture`).
