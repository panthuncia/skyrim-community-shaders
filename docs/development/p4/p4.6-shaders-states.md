# P4.6: shaders, input layouts, state objects and queries

RE for [org-full-port.md](../org-full-port.md) P4.6, done 2026-11-10 with GhidraMCP on SE 1.5.97 and AE 1.6.1170. IDs are
Address Library IDs. It extends R2 and R11 in [engine-d3d11-surface.md](../engine-d3d11-surface.md) and corrects one row of
R11: 75590 is not a query (it makes the swap chain's views). The code is in `src/RenderGraph/Engine/Pipeline/`.

Functions renamed in Ghidra (they were `FUN_`): SE and AE `BSGraphics::Renderer::LoadVertexShader`, `CreateVertexShader`,
`CreatePixelShader`, `LoadPixelShader`, `LoadComputeShader`, `CreateInputLayout`, `AcquireOcclusionQuery`, `BeginQuery`,
`EndQuery`, `GetQueryData`; SE `CreateDepthStencilStates`, `CreateRasterizerStates`, `CreateSamplerStates`.

## Shader creation

All five use the device global (SE 524729 / AE 411348), not `RendererData+0x38`. The shader objects come from the engine's
heap (`MemoryManager::Allocate`).

| SE ID / addr | AE ID / addr | Signature | Device call | Result |
| --- | --- | --- | --- | --- |
| 75547 `0x140d6f6e0` | 77348 `0x140e4a3e0` | `VertexShader* LoadVertexShader(?, BSIStream*)` | CreateVertexShader (slot 12) | `VertexShader+0x08`; bytecode kept at `+0x68`, size `+0x10` |
| 75548 `0x140d6f8a0` | 77349 `0x140e4a5a0` | `VertexShader* CreateVertexShader(?, bytes, size, ?, vertexDesc)` | CreateVertexShader | `+0x08`; bytecode kept |
| 75551 `0x140d6fa00` | 77352 `0x140e4a700` | `PixelShader* CreatePixelShader(?, bytes, size)` | CreatePixelShader (slot 15) | `PixelShader+0x08` (0x80-byte object) |
| 75552 `0x140d6fab0` | 77353 `0x140e4a7b0` | `PixelShader* LoadPixelShader(?, BSIStream*)` | CreatePixelShader | `+0x08`; the bytecode is read into scrap memory and **freed after creation** |
| 75556 `0x140d6fda0` | 77357 `0x140e4aaa0` | `ComputeShader* LoadComputeShader(?, BSIStream*)` | CreateComputeShader (slot 18) | `ComputeShader+0x60`; bytecode kept at `+0x90`, size `+0x6c` |

Callers (SE): 75547 and 75552 from `BSShader::LoadShaders` (101339) and the image-space loaders `FUN_14130a8a0` /
`FUN_14130aa30`; 75548 and 75551 only from `BSMovie::CreateTileTextures` (Bink's tile copy shaders); 75556 from
`BSComputeShader`. The stream format starts with the magic `0x11223344`, then the size, the id, the descriptor fields and
three constant-group size classes that index the pooled constant buffers (R3).

Pixel shader bytecode is gone once 75552 returns, so a description cannot be made from the shader object. It is taken at the
device: `ID3D11Device::Create{Vertex,Pixel,Compute}Shader` are detoured (only with `CS_ORG_ENGINE_SHADERS=1`) and every shader
created on the device is recorded, CS's own included. The engine functions above are detoured after that only to put a
tripwire handle into the object's field.

CS replaces most engine shaders at bind time (`BSShader__BeginTechnique_SetVertexShader/SetPixelShader` in `Hooks.cpp`) with
shaders `ShaderCache::MakeAndAdd*` builds (FXC DXBC, or a DXC container with SPIR-V when `CS_SHADER_DXC` selects it). Those
shaders are CS-owned `BSGraphics::*Shader` objects and are bound through `globals::d3d::context`. Their source (file, defines,
type, descriptor) is recorded from `MakeAndAdd*`. They get no handles: only engine fields do.

`RendererShadowState.currentVertexShader` (RSS+0x348) holds the **vanilla** vertex shader even while CS's replacement is bound
(`State::customVertexShader`). `SetDirtyStates` builds input layouts against that vanilla shader's bytecode.

## Input layouts

`CreateInputLayout(uint64 key)`: SE 75583 `0x140d70f90` / AE 77389 `0x140e4bf20`. Called only from `SetDirtyStates` (75580 /
77386) on dirty bit 0x400 when the key `currentVertexShader->vertexDesc & RSS.vertexDesc` is not in the cache (hash map SE
512147 `0x141e07140` / AE 388957 `0x14202b170`). It builds up to 16 elements from the key (rules in R1) and calls
`device->CreateInputLayout` (slot 11) against `currentVertexShader+0x68`. Key `0x300000000407` may map to null. Layouts are
never released. The particle draws (75490 / 75491) create two more layouts inline, cache them in SE 524736 / 524737 and insert
them under the current key.

The key has no stride (bits 0-3 are zero in a vertex shader mask), so a layout does not know its buffers' strides: the
geometry's `VertexDesc` gives them at draw time.

## State tables

Built once by `BSGraphics::Renderer::InitD3D` (SE 75595 `0x140d72810`; inlined in AE `Renderer::Init` 77226 `0x140e423e0`)
through `RendererData+0x38`, in this order: blend (SE `0x140d88720`, the function CS hooks as "InitD3D" at 75595+0x50 / AE
77226+0x2BC), depth-stencil, depth-bias offsets, rasterizer, samplers. Released by 75832 / 77654.

| Table | SE ID | AE ID | Shape | Index (SetDirtyStates) |
| --- | --- | --- | --- | --- |
| Depth-stencil | 524747 | 411362 | `[6 depth][40 stencil]` | `depthMode*40 + stencilMode` |
| Rasterizer | 524748 | 411363 | `[2 fill][3 cull][12 bias][2 scissor]` | `((fill*3+cull)*12+bias)*2+scissor` |
| Blend | 524749 | 411364 | `[7 mode][2 a2c][13 write][2 extra]` | `((mode*2+a2c)*13+write)*2+extra` |
| Sampler | 524751 | 411366 | `[6 address][5 filter]` | `address*5 + filter` |
| Bias viewport offsets | 524744 | (AE `0x143286a80`) | `float[12]` | `MaxDepth -= offset[bias]` |

The blend factor `SetDirtyStates` passes is SE 512153 `0x141e07168` / AE 388963 `0x14202b198`: four 1.0 floats that nothing
writes. The sample mask is always `0xffffffff`.

CS changes these tables at runtime, so a table entry is not fixed:

- `Deferred::OverrideBlendStates` / `ResetBlendStates` swap the whole blend table for deferred variants (independent blend,
  RT1/RT2 alpha blending) around the G-buffer pass.
- `ShadowmapRasterizerFix` copies the rasterizer table aside and writes per-cascade clones (other depth bias) into it.
- The device's `CreateSamplerState` is detoured right after the blend table is built (the `InitD3D` hook), so the sampler
  table is created with the anisotropy cap (max 8). That detour now lives in `Engine/Pipeline/EngineHooks.cpp`.

**When the tables get handles.** The blend table is built before the guest is installed (CS's hook sits on it), and the
other tables and the query pools after it. `InstallEngineHandlesOnce` runs from CS's hook on `Renderer::Init`'s last call
(`BSGraphics::State`'s setup, SE 75445+0x310 / AE 77226+0x9C3), after the query pools. It marks itself done only once it
wrapped the tables. Deferred's blend copies and `ShadowmapRasterizerFix`'s backup are taken later, at first use, so they
hold the handles. See [p4.1-tripwire.md](./p4.1-tripwire.md) ("Startup order").

Descriptions of state objects are therefore made from the object (`GetDesc`) on first lookup, whichever table or copy holds it.
DXVK caches state objects by description and never frees them, so a state object's address identifies its description.

### What Phase 5 does with them

- **Occlusion:** one rhi `QueryType::Occlusion` pool of 64. The ORG pass that replays the occlusion draw records
  `BeginQuery`/`EndQuery` on the slot the engine acquired, then `ResolveQueryData` into a readback buffer. `GetQueryData`
  returns the resolved value once the frame retired; the blocking form must wait for that frame instead of spinning.
  Done for the sun and the decal test in Phase 5.5.5 ([p5/occlusion-queries.md](../p5/occlusion-queries.md)), with a pool range per frame slot of
  the client's runs instead of one pool mirroring the 64 entries: a kept recording names its frame slot's queries.
- **Timestamp and disjoint:** unused by the engine. If they come back, rhi `QueryType::Timestamp` pools; disjoint has no
  object (frequency from the queue, never disjoint).
- **Event:** a timeline value the ring waits on (P4.5).

## What `CS_ORG_ENGINE_SHADERS=1` does

1. Detours the device's shader and input-layout creation and records a description of each object: the bytecode and its
   128-bit hash (`HashShaderBytes`), the SPIR-V of a DXC container, reflection on demand (`Util::ReflectShader`), and the
   input elements converted to an `org::PipelineInputLayout`.
2. `ShaderCache::MakeAndAdd*` adds each CS shader's source: file, compile defines (`ShaderCache::GetCompileDefines`), type
   and descriptor.
3. With the guest context installed (P4.1, `CS_ORG_TRIPWIRE_GUEST=1`), puts tripwire handles that wrap the real objects into
   the engine's fields: shader objects from the five creation functions, layouts from `CreateInputLayout`, the four state
   tables and the two query pools at the end of `Renderer::Init`. Without it, nothing in the engine changes.
4. The lookup API (`Engine/Pipeline/Descriptions.h`): `FindShader`, `FindInputLayout`, `FindBlend`, `FindDepthStencil`,
   `FindRaster`, `FindSampler`, `FindQuery` take a handle or a D3D11 object; `EngineDrawState::Latch` reads the shadow
   state, `Resolve` turns it into descriptions, `PipelineKey` hashes them and `PipelineStates` fills the state half of an
   `org::GraphicsPipelineDesc`.

## Traps for Phase 5

- CS code that binds a vanilla engine shader through `globals::d3d::context` (raw DXVK) must `Tripwire::Unwrap` it:
  `Hooks.cpp` BeginTechnique thunks and `TerrainBlending.cpp` were changed. Anything new that does the same crashes in DXVK
  with handles installed.
- `org::GraphicsPipelineDesc` has one define list for every stage. Engine vertex and pixel shaders have different defines
  (`VSHADER`/`PSHADER` and descriptor bits), so Phase 5 compiles stages on their own (as DCLF's `ShaderPrograms` does) or ORG
  gains per-stage defines.
- The rasterizer tables' scissor column has no rhi equivalent: a scissor-off draw needs a full-target scissor.
- D3D11 `MultisampleEnable`/`AntialiasedLineEnable` are not carried.
- Input layouts carry no strides; the key must include the geometry's strides or the pipeline must take dynamic strides.
- Vulkan matches inputs by location. `AssignLocations` matches the layout's semantics against the vertex shader's input
  signature; DXC's numbering of a build for ORG must be checked against it.
- The particle layouts (75490 / 75491) are made by the device hook but are not handles: they are cached outside
  `CreateInputLayout`.
